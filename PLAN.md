# Hule — Implementation Plan

**Status:** partial implementation. The Rust crate, schema-version-2 TOML parser, retention rules, Cargo metadata discovery for Rust `target`, single/all-project preview, read-only `hule doctor` configuration report, project registry commands, and an informational JSON plan output exist. A locked Nix flake package and Home Manager wrapper are configured; the package build and CLI `--help` run have passed, but neither Home Manager nor nix-darwin has been activated. Non-authorizing Nix store/profile inspection and narrowly scoped Nix store-object planning/apply exist as M1. M2 generation plan/apply is accepted for the tested Nix 2.34.6 capability row after native guest acceptance and independent safety review; no other Nix version is supported. Profile history removal is not transactional, Hule does not serialize concurrent Nix writers or Home Manager activation, and no reclaimed-byte guarantee is made. Rust cleanup and most providers do not exist. An explicit Docker system-purge plan/apply provider is implemented with mock-runner tests, but its native execution has not been validated and no daemon has been contacted. This plan distinguishes implemented behavior from approved policy and future work; a preview result never authorizes deletion.

Hule is an independent Rust CLI for managing development artifacts and machine cleanup. Mole is reference material only: Hule will not wrap or invoke its CLI, depend on it at runtime, or copy/translate its implementation. Existing work in this local Hule project and in `~/dotfiles` must be preserved. Preserve `~/dotfiles/scripts/disk-cleanup.sh` without overwriting or silently absorbing it.

## Current implementation

- Rust crate and lockfile exist. The local CLI supports `--help`, `--version`, read-only `doctor --config PATH [--json]`, non-authorizing `inspect nix-store` and `inspect nix-generations`, `config preset minimal|developer`, `project register|list|unregister`, and `preview rust-target --config PATH (--project NAME | --all) [--state PATH] [--profile low|normal|aggressive] [--json]`. `--all` previews registered projects in deterministic name order; it does not scan the filesystem, and an empty registry succeeds without invoking Cargo.
- Schema-version-2 TOML policy parsing validates explicit per-profile category lists, profile/category values, and additional keep paths. Version-1 project state is parsed and persisted separately with strict validation, atomic save, and exclusive locking.
- Retention evaluation implements protected-path precedence, persistent-project retention for low/normal, persistent eligibility for aggressive, ephemeral eligibility, and skip for unregistered projects.
- The Rust-target provider runs only for registered projects with `rust_target` enabled and not already protected. Hule invokes `cargo metadata --no-deps --offline --locked` (also passing format-version and manifest-path arguments) and accepts only an existing real target directory contained within the canonical registered root and distinct from the root. It does not request build/clean, enumerate target contents, or execute cleanup. Cargo documentation does not formally guarantee absence of all side effects or code execution by the subprocess. Unsupported states fail closed with generic reporting. `retention-eligible` is not authorization.
- Hule has a Nix flake package (`hule`) and Rust development shell for aarch64-darwin, x86_64-darwin, aarch64-linux, and x86_64-linux. It uses nixpkgs-unstable for aarch64-darwin/Linux and a separate nixpkgs 26.05-darwin input for x86_64-darwin, the last Nixpkgs release supporting that architecture. Its source filter excludes `.git` and only the root `target` directory while retaining other path-source checkout files, including untracked crate files; the successful build from `path:$PWD` verifies the local source. `nix flake check --all-systems --no-build --no-write-lock-file`, `nix build --no-link`, and the package's CLI `--help` run have passed. The Home Manager package list has a local-checkout wrapper that runs the flake after checking for `flake.nix`; neither Home Manager nor nix-darwin has been activated. The Docker system-purge provider now exists as a separate explicit plan/apply action with endpoint/version binding and typed TTY confirmation; native acceptance remains pending. Other cleanup providers remain unimplemented. M2 generation apply is accepted only for the Nix 2.34.6 capability row after its isolated native matrix and independent safety review.

## Goals

1. Provide persistent and ephemeral project-retention modes without cleanup on directory exit or direnv unload.
2. Provide reusable machine cleanup profiles with configurable scope and explicit protected paths/resources.
3. Cover only explicitly approved developer-tool and macOS cache categories; never infer disposable data from generic directory names.
4. Preview proposed actions and clearly explain eligibility, protection, skips, and unsupported behavior before any future apply operation.
5. Integrate Hule and declarative policy with `~/dotfiles` Home Manager after the safety and provider work is reviewed.

## Confirmed decisions

- Name: **Hule** (`hule`), an independent Rust project. Mole source was inspected as inventory/safety reference only; do not import its implementation or create an unexamined licensing obligation.
- Persistent projects keep artifacts in low/normal profiles; aggressive may make eligible build artifacts eligible for further checks unless protected. Ephemeral cleanup is explicit, never triggered by leaving a directory.
- Protected paths/resources take precedence across profiles. Source, toolchains, credentials, and valuable application/project data are not generic cleanup candidates.
- Presets generate explicit TOML, and execution uses saved lists rather than re-discovering targets from a preset.
- High-impact categories are opt-in. Cargo dependency caches are shared across projects: keep them by default and make aggressive Cargo-cache cleanup opt-in.
- Nix store contents may be reclaimed only through narrowly selected Nix store deletion with native reachability checks, never direct filesystem deletion. M2 is a separate exact-ID history-link operation; it must not activate profiles, delete store objects, or run GC.
- The fixed Docker system purge is a separate explicit operation, selected only by `hule plan docker --docker-purge` and the aggressive-only `docker_purge` category. It requires an explicitly selected canonical Docker CLI executable and a verified local Unix socket whose parent directories prevent replacement by other principals; it rejects inherited endpoint/context/API/config/TLS overrides, binds executable/socket/parent identities plus Docker CLI/Engine/API versions and Engine ID, requires API 1.42+, saves a private versioned plan outside the daemon data root, and demands typed TTY confirmation plus immediate identity/policy revalidation. Same-UID adversaries and pathname races against same-UID changes are not prevented. It invokes only `docker system prune --all --volumes --force`; the daemon dynamically selects stopped containers, unused networks, all unused images, build cache, and unused anonymous volumes. It has no per-resource preview or rollback, may partially mutate on error, reports unknown outcome and never retries. This broad selection is authorized only by that explicit opt-in; it is never a fallback. OrbStack machine deletion/reset and future granular Docker actions remain separate scopes.
- No default age thresholds. Define age semantics only per provider when reliable usage metadata exists; file mtimes alone do not establish that an artifact is unused.
- Preserve existing local work, including the untracked `~/dotfiles/scripts/disk-cleanup.sh`. Do not reset, clean, stage, or commit unrelated repository work.

## Policy model and safety requirements

Keep these concepts distinct:

- Project retention: persistent or ephemeral.
- Cleanup profile: low, normal, or aggressive.
- Protected paths/resources: exclusions that apply under all profiles.
- Explicit opt-ins: authorize narrowly scoped high-impact categories; they do not replace preview or confirmation requirements.

Use typed, validated configuration. Keep declarative policy separate from mutable project registrations/state. Do not make directory-name heuristics or config globs sufficient authorization to delete arbitrary data. Unknown/unregistered project paths are not cleanup candidates. Presets must produce explicit TOML, and later execution must act on saved candidate lists rather than rediscovering targets from presets.

Protect by default: source repositories and tracked files; `~/.rustup`, installed tools and configuration; credentials, keys, password stores, environment files and tokens; wallets, databases, emulator/VM state, Docker images and VM disks (except unused images explicitly included by the opt-in Docker system purge), valuable project/application data and AI models; browser cookies, login/session data, history, bookmarks, preferences, local storage, extension state and whole profiles; Xcode archives, SDKs, simulator runtimes and simulator device state; active containers and referenced resources; and user-configured protected paths/resources.

Future cleanup work must reject unsafe traversal and dangerous symlink targets, never follow a link outside an authorized root, never execute project-provided cleanup scripts, and revalidate target identity, containment, protections, process/resource activity, and category preconditions immediately before mutation. Fail closed on uncertain provider state or errors; never silently broaden a narrow operation. Reports must not print file contents, secrets, environment values, browser/profile contents or protocol payloads. Mark reclaimed-size estimates as estimates.

### Cargo apply is intentionally blocked

The current Cargo provider only discovers `target_directory`; it does not establish that the directory contains only disposable Cargo artifacts, that it is exclusively owned by the registered project, or that no build is using it. Do not implement Rust apply as `cargo clean --manifest-path ... --target-dir <previewed path>`. Cargo's documented default clean removes the target directory rather than consuming a Hule allow-list, so user-created files inside it may also be removed. Cargo 1.95.0 source at revision `f2d3ce0bd7f24a49f8f72d9000448f8838c4e850` also shows that an unscoped whole-directory clean skips the build-output lock and can remove a separately configured build directory; these are implementation observations, not cross-version guarantees. `--dry-run` is diagnostic, not a stable saved plan or a reservation against concurrent changes. Metadata/clean scope can depend on the invocation working directory, environment, and Cargo configuration. Sources: [Cargo clean manual](https://doc.rust-lang.org/stable/cargo/commands/cargo-clean.html), [Cargo configuration](https://doc.rust-lang.org/stable/cargo/reference/config.html), [pinned Cargo clean implementation](https://github.com/rust-lang/cargo/blob/f2d3ce0bd7f24a49f8f72d9000448f8838c4e850/src/cargo/ops/cargo_clean.rs). Apply must remain unsupported until a separately reviewed mechanism can enumerate and authorize every mutation destination, establish quiescence for the full operation, and revalidate object identity and protections without broadening or relying on Cargo's incidental locking.

## Future provider scope

All items in this section are requirements for future work, not claims of existing provider capabilities.

- **Project artifacts and runtimes:** evaluate explicit Rust `target` and other recognized per-project outputs separately from shared dependency stores, installed runtimes/toolchains, configuration, and offline-critical package downloads. Project-only cleanup must not trigger global cache, Nix, Docker, browser, or machine cleanup.
- **macOS/Xcode/apps:** consider enumerated cache/build/log leaves only, with process checks. Never treat all of `~/Library`, `Application Support`, `/Library`, or `/System` as disposable. Preserve archives, SDKs, device-support installations, simulator runtimes/state, app databases, user documents and models.
- **Browsers:** only explicitly selected cache leaves with browser-specific handling and active-process checks. Preserve all authentication/session stores, history, bookmarks, local storage/IndexedDB, preferences, extensions and profile roots. Skip if process state is unknown; avoid broad Safari/WebKit storage and broad `Application Support` paths.
- **Nix:** M1 is limited to explicit top-level store object inputs and their saved forward-requisites closure; shared requisites are globally deduplicated and every returned path is strictly validated. `nix-store --query --requisites` may open/create/migrate store metadata; it does not intentionally alter roots/objects. Plan output requires an existing parent and is rejected if it lexically or via canonicalized parent aliases overlaps the store. Apply revalidates and checks each saved object present immediately before delete. It reports `removed` only for successful delete command plus post-command absence, and otherwise uses `retained_or_not_deleted`, `absent_after_failure`, or `unknown`; failed/partial commands remain nonzero. `nix-store --delete` retains native liveness/referrer checks but may be non-atomic and performs GC bookkeeping beyond object paths. Native integration uses only a feature-gated test API with explicit `local?root=<canonical TempDir>`; CLI and saved plans remain pinned to `daemon`. Never use direct removal, `--ignore-liveness`, broad GC, system-generation selection, or implicit endpoint fallback. `daemon` may represent a shared/system store; it is not necessarily user-only. M2 generation history is handled by a separate explicit-profile provider.
- **Docker/OrbStack:** Docker has one explicit broad purge action as described above; no generic `system prune` fallback, arbitrary command, context selection, remote endpoint, or preset opt-in exists. The saved plan records a caller-selected canonical Docker CLI path/file identity, the local Unix socket and protected parent-directory identities, Engine ID, Docker CLI/Engine/API versions, and fixed scope; API must be at least 1.42. Parent directories are root/current-user-owned and non-writable by group/others, except root-owned sticky directories. Apply uses TTY typed confirmation, reloads policy, revalidates identity immediately before one `docker system prune --all --volumes --force` invocation, and reports possible partial mutation honestly without retry. It does not prevent a malicious same-UID process or pathname races against same-UID changes. Resource eligibility is dynamic, so there is no per-resource preview or reclaimed-byte guarantee. Native acceptance remains pending; only injected-runner tests have been used. OrbStack machine deletion (`orb delete docker`), machine removal, and `orb reset` remain separate, unimplemented scopes; no machine or Docker daemon was purged during this work.

## CLI and configuration status

Currently supported:

```text
hule --help
hule --version
hule doctor --config PATH [--json]
hule inspect nix-store --config PATH --store-path PATH... [--profile low|normal|aggressive] [--json]
hule inspect nix-generations --config PATH --nix-profile NAME [--generation ID...] [--profile low|normal|aggressive] [--json]
hule config preset NAME
hule project register --name NAME --path PATH --mode persistent|ephemeral [--state PATH]
hule project list [--state PATH]
hule project unregister --name NAME [--state PATH]
hule preview rust-target --config PATH (--project NAME | --all) [--state PATH] [--profile low|normal|aggressive] [--json]
hule plan nix-store --config PATH --store-path PATH... --output PLAN [--profile low|normal|aggressive]
hule plan nix-generations --config PATH --nix-profile NAME --generation ID... --output PLAN [--profile low|normal|aggressive]
hule plan docker --docker-purge --config PATH --docker-cli /ABS/PATH/docker --docker-endpoint unix:///PATH --output PLAN [--profile low|normal|aggressive]
hule apply --plan PATH --config PATH [--profile low|normal|aggressive]
```

`hule doctor --config PATH [--json]` parses only the explicit policy and reports configured categories, configured Nix profile names, and static capability limits. It does not invoke providers, check host compatibility, inspect host paths or authorize cleanup. Invalid/unreadable configuration is reported as `unsafe` without echoing paths or contents. `available` means the local capability is implemented; `unchecked` means runtime/host compatibility was not tested; unsupported providers remain explicit.

Schema version 2 has `schema_version`, `default_profile`, required `[profiles.low]`, `[profiles.normal]`, and `[profiles.aggressive]` tables with explicit `categories` arrays, and optional absolute `additional_keep_paths`; it does not contain project registrations. Project registry state is version 1 TOML with project names mapped to canonical absolute paths and `persistent`/`ephemeral` modes. The optional `--state PATH` selects the separate state file for preview and project commands. Registry updates hold the sidecar lock across load, validation, mutation, and atomic replacement. The supported categories are `rust_target`, `nix_store_gc`, `nix_user_generations`, `nix_home_manager_generations`, and `docker_purge`; all remain explicitly opt-in, and `docker_purge` is restricted to the aggressive profile. `hule config preset minimal|developer` prints complete TOML and does not write files. Project names are ASCII letters, digits, `_`, or `-`. Registered roots cannot overlap. Missing state means an empty registry. The optional CLI profile overrides `default_profile`. Unknown projects are skipped without constructing a target path. `--project NAME` and `--all` are mutually exclusive and exactly one is required; `--all` traverses the registry's BTreeMap order and emits a delimited report for each registered project, with an explicit successful empty-registry result. CLI registration/list/unregister are implemented; explicit migration remains outstanding and inline registrations are not imported. See `README.md` for an example.

Implemented discovery/inspection includes Cargo metadata for registered Rust projects and explicit non-authorizing Nix store/profile inspection. Nix inspection has no saved action-plan format and does not delete or authorize cleanup; queries may open/create/migrate Nix store metadata, store scope and reclaimed bytes remain unchecked, and generation inspection is limited to Nix 2.34.6. Hule invokes `cargo metadata --no-deps --offline --locked`; it requests no build/clean and runs no cleanup, but Cargo documentation does not formally guarantee zero side effects or code execution. Not implemented: Rust target content enumeration/apply, general cleanup, explicit migration, OrbStack-specific, macOS/browser/shared-cache providers. Docker's explicit broad system-purge plan/apply is implemented but native execution acceptance is pending. M1 implements a separate Nix store-object plan/apply path; M2 generation plan/apply is accepted only for Nix 2.34.6 after its isolated native matrix and independent safety review. No other Nix version is supported. JSON output is limited to the informational preview plan and is not an apply input. Project registration/list/unregister commands and transactional state updates are implemented. Explicit migration is deferred; legacy inline registrations are not imported. The Nix flake package build and CLI `--help` run have passed; Home Manager activation has not been performed.

## Testing and validation requirements

Use temporary fixtures and mocked providers; never run cleanup on real user data in tests. Future tests must cover profile selection, persistent/ephemeral semantics, keep-rule precedence, unknown projects, candidate containment, symlinks, traversal, paths with spaces, active processes, permission errors, missing tools, and preview/apply revalidation. Browser fixtures must prove profile/authentication data is never selected; Xcode fixtures must distinguish DerivedData from archives, SDKs, simulator state and runtimes. Docker unit fixtures must use an injected runner and prove no daemon access; cover aggressive-only opt-in, strict saved-plan dispatch/duplicate-key rejection, exact local Unix endpoint and identity/API revalidation, inherited override rejection, exact fixed prune arguments, typed confirmation, no retries, dynamic/partial-result reporting, and output-path safety. Do not use a real Docker or OrbStack daemon for these tests. M1 Nix tests cover native store-object deletion and GC bookkeeping; M2 tests must prove exact history-link removal with no activation, store-object deletion, or explicit GC operation.

Run `cargo fmt --all --check`, `cargo clippy --all-targets --all-features -- -D warnings`, and `cargo test --all-features` for applicable Rust changes, plus focused fixtures and Nix evaluation/build checks when those features exist. Never use real machine-wide cleanup as validation. Review public CLI/config behavior, report privacy, and fail-closed behavior before adding providers.
